# М'ясна Лавка — інтернет-магазин м'ясної продукції

Повноцінний production-ready магазин: публічний сайт, база даних, бекенд, кошик,
оформлення замовлення та **прихована адмін-панель**, до якої звичайний відвідувач
не має жодного доступу.

**Стек:** Next.js 15 (App Router) · React 19 · TypeScript · Tailwind CSS · PostgreSQL · Prisma · Zod

---

## 1. Швидкий старт

```bash
# 1. Залежності
npm install

# 2. Налаштування
cp .env.example .env
#    відкрийте .env і змініть AUTH_SECRET, ADMIN_PASSWORD та ADMIN_PATH
#    згенерувати секрет: openssl rand -base64 48

# 3. База даних (потрібен Docker; або вкажіть свій DATABASE_URL)
docker compose up -d

# 4. Схема + демо-наповнення: 10 категорій, 32 товари, 24 замовлення
npm run setup

# 5. Запуск
npm run dev
```

Сайт: <http://localhost:3000>
Адмінка: <http://localhost:3000/kabinet> (шлях задає `ADMIN_PATH`)

Логін і пароль першого адміністратора беруться з `.env`
(`ADMIN_EMAIL`, `ADMIN_PASSWORD`) під час `npm run setup`.

## 2. Як захищена адмін-панель

Вимога була проста: **клієнти не мають бачити адмінку, вона тільки для власника.**
Реалізовано чотирма незалежними рівнями — прихований URL сам по собі нічого не захищає,
тому на нього ніхто не покладається.

| Рівень | Що робить |
|---|---|
| **Прихований шлях** | Адмінка живе за адресою з `ADMIN_PATH` (наприклад `/kabinet`). Якщо значення не `admin`, то прямий запит на `/admin` повертає **404** — сторонній навіть не дізнається, що адмінка існує. |
| **Middleware** | Кожен запит до адмін-зони перевіряє підписану сесію (JWT у httpOnly-cookie). Немає сесії — редирект на форму входу, до коду адмінки запит не доходить. |
| **Перевірка в діях** | Кожна серверна дія викликає `requireAdmin('permission')`. Навіть якщо хтось підробить запит напряму до server action, він отримає відмову. |
| **Ролі (RBAC)** | `OWNER` бачить усе, `MANAGER` — замовлення й клієнтів, `CONTENT` — товари й тексти. Пункти меню й дії, недоступні ролі, не рендеряться і не виконуються. |

Додатково: у публічному сайті **немає жодного посилання** на адмінку;
адмін-сторінки віддають заголовок `X-Robots-Tag: noindex`, а `/robots.txt`
забороняє індексацію цього шляху.

**Щоб змінити адресу адмінки** — відредагуйте два рядки в `.env` і перезапустіть застосунок:

```env
ADMIN_PATH="moya-tayemna-adresa"
NEXT_PUBLIC_ADMIN_PATH="moya-tayemna-adresa"
```

Захист входу: пароль зберігається хешем bcrypt (12 раундів), обмеження 5 спроб
на хвилину з однієї IP, після 5 невдалих спроб обліковий запис блокується на 15 хвилин.

## 3. Що вміє магазин

### Кабінет покупця
- Реєстрація, вхід, вихід, відновлення пароля одноразовим посиланням (у базі — лише хеш токена)
- Профіль, зміна пароля, збережені адреси доставки
- Історія замовлень із кнопкою **«повторити замовлення»** — усі позиції повертаються в кошик
- Обране, синхронізоване між пристроями (не localStorage, а база)
- Відгуки з модерацією: покупець залишає, адміністратор публікує, рейтинг товару перераховується
- Замовлення, зроблені раніше без реєстрації, підтягуються в кабінет за номером телефону
- Оформити замовлення так само можна **без акаунта** — він лишається необов'язковим

### Публічна частина
- Головна: hero, категорії, хіти, акції, новинки, переваги, відгуки, FAQ, підписка
- Каталог із фільтрами (вид м'яса, тип, ціна, наявність, акція, новинка, рейтинг),
  сортуванням і пагінацією — **весь стан у query-параметрах**, посилання можна надіслати
- Живий пошук із підказками (фото, назва, ціна) і частковими збігами
- Сторінка товару: галерея, вибір ваги, повзунок довільної ваги, кількість,
  характеристики, харчова цінність, відгуки, схожі товари, Schema.org
- Кошик, що **зберігається на сервері** й переживає перезавантаження та зміну пристрою
- Оформлення без реєстрації, серверна валідація, промокоди, прогрес до безкоштовної доставки
- Сторінка замовлення зі статусом, юридичні сторінки, 404 і 500

### Адмін-панель
- Дашборд: виторг, замовлення, середній чек, графік продажів, товари на межі залишку
- Замовлення: фільтри, пошук, зміна статусу за дозволеними переходами, історія, коментар менеджера
- Товари: створення, редагування, дублювання, приховування, видалення, журнал рухів залишку
- Категорії, клієнти (CRM з історії замовлень), промокоди, залишки з коригуванням
- Модерація відгуків: опублікувати, відхилити, повернути на перевірку
- **Налаштування**: назва магазину, контакти, соцмережі, тексти головної, SEO,
  поріг безкоштовної доставки, мінімальна сума — усе редагується без розробника

## 4. Логіка, на яку варто звернути увагу

### Ціна й вага
М'ясо продається п'ятьма способами, і кожен коректно проходить шлях
каталог → кошик → замовлення → списання залишку:

| Режим | Ціна вводиться | Покупець бачить |
|---|---|---|
| `PER_KG` | за кілограм | «640 ₴ / кг» + вибір 500 г, 1 кг, 2 кг або довільна вага |
| `PER_100G` | за 100 г | «89 ₴ / 100 г» |
| `PER_UNIT` | за штуку | «260 ₴ / шт» |
| `PER_PACKAGE` | за упаковку | «165 ₴ / уп. 400 г» |
| `SET` | за набір | «BBQ Set · 2,4 кг · 1 290 ₴» |

Розрахунок живе в одному місці — `src/services/pricing.ts` — і викликається скрізь.
Фронтенд ніколи не рахує суму сам: показує те, що повернув сервер.
**Гроші зберігаються цілим числом у копійках**, вага — цілим числом у грамах.

### Замовлення
Створюється в одній транзакції зі списанням залишків і записом у журнал рухів.
Якщо залишку не вистачило — транзакція відкочується цілком. Статус змінюється лише
за дозволеними переходами; скасування повертає залишки на склад і відкочує промокод.
У `OrderItem` зберігаються **знімки** назви, фото й ціни — старе замовлення завжди
виглядає так, як його бачив клієнт.

### Налаштування
Читаються один раз і кешуються з теговою інвалідацією: збереження в адмінці скидає
тег `site-settings`, наступний запит бере свіже значення. У коді немає жодного
захардкодженого телефону чи назви.

## 5. Онлайн-оплата

Підключено **LiqPay**; архітектура розрахована на будь-якого провайдера.

**Як увімкнути:** візьміть ключі в кабінеті LiqPay і впишіть у `.env`:

```env
LIQPAY_PUBLIC_KEY="ваш_public_key"
LIQPAY_PRIVATE_KEY="ваш_private_key"
LIQPAY_SANDBOX="1"   # 0 — бойовий режим
```

Спосіб оплати вважається онлайновим, якщо в таблиці `PaymentMethod` заповнене поле
`provider` (для «Банківська картка» та «Apple Pay / Google Pay» це `LiqPay`).
Після оформлення такого замовлення покупця перекидає на `/order/<номер>/pay`,
звідки форма веде на захищену сторінку LiqPay — **дані картки на наш сайт не потрапляють.**

**Вебхук:** `POST /api/payments/liqpay`. Підпис перевіряється завжди
(`sha1(private + data + private)`), і без збігу запит відхиляється з кодом 400 —
інакше будь-хто міг би позначити чуже замовлення оплаченим. Успішна оплата ставить
`paymentStatus = PAID`, переводить замовлення з «Нове» в «Підтверджено» й пише подію в історію.

У проді вкажіть публічну адресу сайту в `NEXT_PUBLIC_SITE_URL` — з неї будуються
`result_url` і `server_url` для провайдера.

**Щоб додати WayForPay чи Fondy:** створіть сусідній модуль у `src/services/payments/`
з функціями `buildCheckout` і `verifyCallback`, зареєструйте його в `PROVIDERS`
(`src/services/payments/index.ts`) і вкажіть назву в полі `provider` способу оплати.
Решта коду не змінюється.


## 7. Фотографії товарів

Зараз зображення генеруються процедурно (`/api/img/<форма>/<відтінок>/<seed>`) —
у кольорах бренду, щоб каталог виглядав цілісно до появи справжніх знімків.

Щоб підставити реальні фото: покладіть файли в `public/uploads/` і вкажіть шлях
у полі «Головне фото» в картці товару в адмінці. Решта коду не змінюється.
Для кількох фото на товар додайте записи в таблицю `ProductImage`.

## 9. Деплой

**Vercel + керована PostgreSQL (Neon, Supabase, Railway)** — найшвидший шлях:

1. Створіть базу, скопіюйте `DATABASE_URL`
2. У змінних оточення Vercel задайте `DATABASE_URL`, `AUTH_SECRET`,
   `ADMIN_PATH`, `NEXT_PUBLIC_ADMIN_PATH`, `NEXT_PUBLIC_SITE_URL`
3. Перед першим деплоєм виконайте `npx prisma migrate deploy` і `npm run db:seed`
4. Задеплойте — `npm run build` виконає `prisma generate` автоматично

**Власний VPS:** `docker compose up -d` для бази, далі `npm ci && npm run build && npm start`
за reverse-proxy (nginx/Caddy) з HTTPS.

Перед публічним запуском обов'язково:
- змініть `AUTH_SECRET` і пароль адміністратора;
- змініть `ADMIN_PATH` на непередбачуваний;
- узгодьте тексти юридичних сторінок із юристом;
- підключіть платіжного провайдера (місце підключення — `src/app/api/`) і
  поштовий сервіс (`src/services/notifications.ts`, змінна `EMAIL_PROVIDER_KEY`).

## 10. Що ще не реалізовано

Свідомо залишено на наступний етап:

- **Реальна відправка листів.** Черга сповіщень працює (таблиця `Notification`,
  повторні спроби), Telegram надсилається по-справжньому — лишилось підключити
  поштового провайдера: одна функція в `src/services/notifications.ts` і ключ
  `EMAIL_PROVIDER_KEY`. Поки ключа немає, посилання для відновлення пароля
  показується прямо на сторінці в режимі розробки.
- **Нарахування й списання бонусів.** Поле `bonusBalance` є й показується в кабінеті,
  правил нарахування ще немає.
- **Друга мова інтерфейсу.** Тексти зібрані в компонентах, готові до винесення в `i18n/`.
- **Завантаження фото через адмінку.** Зараз вказується шлях до файлу;
  форма з drag-and-drop і обробкою в WebP/AVIF — окремий крок.

### Демо-доступи після `npm run setup`

| Роль | Логін | Пароль |
|---|---|---|
| Власник магазину | значення `ADMIN_EMAIL` | значення `ADMIN_PASSWORD` |
| Демо-покупець | `olena@example.com` | `Demo12345!` |

У демо-покупця вже є історія замовлень, дві адреси й три товари в обраному —
зручно перевіряти кабінет одразу після встановлення.
